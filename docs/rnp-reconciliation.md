# РНП по шаблону «МойСклад» и сверка отчётов

## Полученный шаблон и решение пользователя

20.10.2026 получен файл `РНП (юнитка) для маркетплейсов от [МойСклад].xlsx`. Оригинал сохранён как `templates/rnp-moysklad-original.xlsx`, извлечённые заголовки, координаты, формулы, примечания и контрольные значения — `fixtures/rnp-template.json` (SHA-256 оригинала внутри). Google-таблица больше не нужна для чтения этих колонок.

Вкладка РНП содержит шесть расчётных листов: «Товары» (14 колонок), WB FBW (24), WB FBS (21), Ozon FBO (21), Ozon FBS (22), «Сравнить» (17). Порядок колонок и объединённые заголовки сохранены. Пустые строки до 1000 и рекламные/справочные листы не дублируются в интерфейсе. Лист «Товары» содержит 13 товаров; в некоторых листах исходника есть дополнительная строка с `#REF!`, она сохранена с пометкой отсутствия данных.

**Указание пользователя:** закупочные цены и остальные исходные числа оставить примером. При подключении API WB/Ozon сначала запросить у владельца файл закупочных цен с артикулами. Не считать текущие цены рабочими и не спрашивать файл повторно до этапа подключения. Налоговый режим и ставку нужно уточнить у селлера; пользователь их пока не знает. Напоминание также отображается в «Интеграциях» и пояснениях РНП.

Примечание автора в WB FBW!T2 и WB FBS!Q2: «В шаблоне приведен самый простой пример с УСН по доходам. Для автоматического расчета надо в формуле подставить ставку УСН. В нашем примере 6+1=7%». Значение дополнительного 1% автор **не объясняет**. 7% сохранены только как допущение примера, а не подтверждённая налоговая ставка продавца. В исходнике WB налог считается от цены после скидки и СПП, Ozon — от цены после скидки; это формулы учебного калькулятора, не проверенная налоговая модель. В параметрах можно задать расчётную ставку, но сложный режим требует отдельной реализации.

Формулы вычисляются ограниченным арифметическим парсером без `eval`, по исходным координатам с поддержкой ссылок между листами. Фиксированные ссылки на первую базовую ставку (`$K$4` в WB FBS, `$J$4` в Ozon FBO) сохранены и объяснены, чтобы не менять экономику исходника молча. Пустая закупка, неразрешимые/циклические ссылки и деление на ноль дают «—». Пустые дополнительные собственные затраты F:K листа «Товары» считаются нулевыми согласно комментариям файла. Другие неизвестные тарифы не превращаются в ноль. Явный ноль остаётся числом.

Редактируются исходные ячейки, зависимые формулы пересчитываются. Изменения сохраняются в браузере отдельно от отчётов. XLSX-экспорт — **снимок вычисленных значений**, шесть листов и лист происхождения; не копия исходного файла со сломанными формулами. Отдельная юнит-экономика SELLER MOON сохранена без изменений.

## Источники колонок

| Колонки | Источник при подключении | Что проверить |
| --- | --- | --- |
| Название, артикул, штрих-код | Каталог WB/Ozon | offer_id / SKU / артикул продавца, без сопоставления по одному названию |
| Группа товаров | Категория МП или ручная группа | Категория кабинета может отличаться от внутренней группы |
| Закупка, посредник, брак, доставка до МП, маркировка, собственное хранение, упаковка | Файл владельца / ручной ввод | Стоимость на единицу, дата действия, связь по артикулу |
| Текущие остатки | Остатки WB/Ozon | Различать FBW/FBO/FBS и склады; сумма себестоимости вычисляется |
| Цена до скидки, скидка, цена после скидки, СПП | Цены и детализация операций МП | Каталожная цена и историческая цена продажи различаются; СПП не оценивать без источника |
| Комиссия, логистика, хранение, приёмка, последняя миля, обработка, эквайринг | Финансовые операции / актуальные тарифы МП | Фактическая сумма не равна базовому тарифу; разные единицы и даты признания |
| Выкуп, средние дни хранения | Историческая статистика либо явный план | Указывать окно наблюдения, возвраты и знаменатель; не выдавать план за факт |
| Продвижение | Рекламный источник WB / Ozon Performance и финансовые удержания | Не задвоить списания; процент из расходов и сопоставимой выручки |
| Налог | Уточнить у селлера | Режим, ставка, база; не получать предположительно из API продаж |
| Себестоимость, выручка после удержаний, прибыль, маржа, ROI, доля себестоимости | Формулы шаблона | Расчёт на единицу, не сумма всех операций за период |

Отдельный лист «Фактические данные» показывает датированные значения отчётов и журнал сверки. Календарь применяется к нему; калькулятор на единицу от дат не зависит. Общие финансовые суммы не подставляются в тарифы на единицу. Автоматическая проекция факта в модель потребует полного, проверенного сопоставления операций, моделей продаж и количеств.

Никакие цифры шаблона не выдаются за полученные из кабинета.

## Правила модуля

1. Ключ ячейки: маркетплейс + кабинет + дата + артикул (или `null` для общего итога кабинета) + показатель. Данные разных кабинетов, маркетплейсов и метрик не смешиваются.
2. Ежедневные значения — `daily-preliminary`. Новая версия ежедневного источника заменяет прежнюю предварительную версию, а не прибавляется к ней.
3. Детализированный закрытый недельный отчёт имеет приоритет по тем ячейкам, которые он действительно подтверждает. Получение более позднего ежедневного отчёта не перезаписывает подтверждённые недельные значения.
4. Для каждого изменения записываются значения до/после, отчёт, версия, источник, время импорта, разница и причина. Даже одинаковые суммы могут менять статус происхождения с ежедневного на подтверждённый недельный.
5. Повторный импорт идентичного отчёта той же версии идемпотентен. Другая сумма под тем же ID и revision запрещена: требуется новая версия. Все предыдущие отчёты остаются в журнале.
6. Если маркетплейс выпустит корректировку закрытого отчёта, она принимается новой revision. Для замены отчёта другим ID требуется явная ссылка `supersedes` на прежний отчёт того же кабинета и периода. Неоднозначные пересекающиеся недельные отчёты и циклы корректировок отвергаются.
7. Недельный отчёт должен быть закрыт и содержать значения по реальным датам. Один общий недельный итог не распределяется равномерно по дням. Нулевые суммы должны быть явно переданы источником; неизвестные значения не превращаются в ноль.
8. Недельная версия, из которой исчезла ранее известная ячейка, помечает её `needs-review` с `null`. Старая ежедневная сумма не восстанавливается автоматически. Метрики, никогда не подтверждавшиеся недельным отчётом, остаются предварительными до получения подходящего источника.
9. Модуль работает с полными снимками ячеек, не с отдельными строками денежных операций. Будущий коннектор обязан забрать все страницы, устранить дубли по ID исходных операций и агрегировать их до передачи. Неуспешная/частичная выгрузка не должна считаться полным отчётом.

Закрытая неделя — основной источник для сверки, но не гарантия отсутствия будущих корректировок от площадки. Периодичность и статус окончательного финансового документа проверяются отдельно для WB и Ozon; произвольный документ Ozon нельзя назвать недельным только ради единой модели.

## Пример нормализованной версии

```js
{
  id: 'ID-отчёта-из-источника',
  marketplace: 'wb',
  accountId: 'ID-кабинета',
  source: 'weekly',
  revision: 1,
  from: '2026-10-12',
  to: '2026-10-18',
  closed: true,
  publishedAt: '2026-10-19T09:00:00Z',
  cells: [{date:'2026-10-12',article:'Артикул',metric:'revenue',value:92}]
}
```

Названия метрик в примере технические; они не заменяют карту реальных колонок пользовательского Excel. Схема внешнего API не угадывается по этому примеру.

## Импорт и серверное хранение

`lib/rnp-store.mjs` сохраняет нормализованные полные отчёты атомарно: блокировка импорта, проверка всего пакета до записи, временный файл с правами 0600, резервная копия `.bak`, затем rename. Повторный импорт не меняет файл. При чтении исходные отчёты повторно проверяются и сверяются; сохранённым вычисленным ячейкам сервер не доверяет. Каталог `data/` игнорируется Git.

```sh
# Команды выполняются в корне проекта. Используйте один абсолютный путь.
export RNP_LEDGER_PATH=/workspace/pult_upravleniya/data/rnp-ledger.json
npm run rnp:import -- /path/to/normalized-reports.json
npm start
```

Вход — один нормализованный отчёт из примера выше или массив отчётов. Это не импорт произвольного финансового XLSX маркетплейса. `GET /api/rnp` отдаёт сверенные ячейки, историю изменений и историю импортов без ключей API. Без пути — пустой статус `disconnected`. При ошибке чтения/проверки — 503, интерфейс сохраняет последний успешный снимок. HTTP-запись не открыта. Нажатие «Обновить отчёты» читает серверный журнал и **не запускает запрос в кабинет**.

Сервер разработки не имеет авторизации. Перед публикацией финансовых данных необходимы аутентификация и разграничение доступа; сам журнал не следует размещать в открытом репозитории.

## Следующий этап подключения

1. По указанию пользователя запросить файл закупочных цен; у селлера уточнить налоговый режим и ставку.
2. Настроить серверные секреты, проверить доступ к официальным API, сопоставить реальные методы и поля с таблицей источников выше.
3. Реализовать коннекторы с пагинацией, защитой от частичных выгрузок, идемпотентностью и раздельным учётом моделей/кабинетов. Для независимых моделей использовать разные имена метрик либо добавить явное измерение модели в контракт до включения источника.
4. Настроить ежедневный сбор изменяемого недавнего периода и повторный сбор опубликованной закрытой детализации. Не называть любой документ Ozon недельным без проверки его периода и статуса.
5. Проверить реальные отчёты на кабинете и только затем включить автоматическое заполнение фактических колонок.
