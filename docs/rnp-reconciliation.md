# РНП: ежедневные данные и сверка с недельными отчётами

## Что доступно сейчас

Подготовлен и протестирован независимый модуль `lib/rnp-reconciliation.mjs`. Он принимает нормализованные ячейки отчётов, выбирает приоритетный источник и ведёт журнал изменений. Это основа сверки, **ещё не подключённая к интерфейсу, расписанию или API маркетплейсов**.

Текущая вкладка РНП продолжает показывать прежний демонстрационный план-факт отчёт. Совпадение её колонок с пользовательской таблицей не заявляется.

## Внешние prerequisites

- Пользовательская таблица: https://docs.google.com/spreadsheets/d/1b4XfkXA8sogUp70W8iuA2Rk-s0yJgWT1WaT1VJKyO5o/edit?usp=sharing
- И HTML, и XLSX-экспорт ссылки заблокированы сетевым прокси: `Tunnel connection failed: 403 Forbidden`. Это не свидетельство неправильных прав самой Google-таблицы. Нужен прикреплённый XLSX либо доступ среды к docs.google.com для чтения настоящих листов, заголовков, формул и форматов. Колонки не придуманы.
- Проверена только установленность переменных; значения не печатались. WB_TOKEN, OZON_CLIENT_ID, OZON_API_KEY не установлены; существующие секретные привязки также отсутствуют.
- В черновике среды сохранены необходимые домены и требования WB_TOKEN, OZON_API_KEY; OZON_CLIENT_ID объявлен обычной переменной. Значения вводятся пользователем в настройках среды, не в чате. Сохранение черновика не подключает API и не публикует среду.

После получения таблицы для каждой реальной колонки нужно определить: API-метод/поле и период признания, вычисляемую формулу или ручной показатель. Пользователю задаются вопросы только по отсутствующим в API бизнес-данным. Перечень этих вопросов нельзя составить достоверно без самих колонок.

## Правила модуля

1. Ключ ячейки: маркетплейс + кабинет + дата + артикул (или `null` для общего итога кабинета) + показатель. Данные разных кабинетов, маркетплейсов и метрик не смешиваются.
2. Ежедневные значения — `daily-preliminary`. Новая версия ежедневного источника заменяет прежнюю предварительную версию, а не прибавляется к ней.
3. Детализированный закрытый недельный отчёт имеет приоритет по тем ячейкам, которые он действительно подтверждает. Получение более позднего ежедневного отчёта не перезаписывает подтверждённые недельные значения.
4. Для каждого изменения записываются значения до/после, отчёт, версия, источник, время импорта, разница и причина. Даже одинаковые суммы могут менять статус происхождения с ежедневного на подтверждённый недельный.
5. Повторный импорт идентичного отчёта той же версии идемпотентен. Другая сумма под тем же ID и revision запрещена: требуется новая версия. Все предыдущие отчёты остаются в журнале.
6. Если маркетплейс выпустит корректировку закрытого отчёта, она принимается новой revision. Для замены отчёта другим ID требуется явная ссылка `supersedes` на прежний отчёт того же кабинета и периода. Неоднозначные пересекающиеся недельные отчёты и циклы корректировок отвергаются.
7. Недельный отчёт должен быть закрыт и содержать значения по реальным датам. Один общий недельный итог не распределяется равномерно по дням. Нулевые суммы должны быть явно переданы источником; неизвестные значения не превращаются в ноль.
8. Недельная версия, из которой исчезла ранее известная ячейка, помечает её `needs-review` с `null`. Старая ежедневная сумма не восстанавливается автоматически. Метрики, никогда не подтверждавшиеся недельным отчётом, остаются предварительными до получения подходящего источника.
9. Модуль работает с полными снимками ячеек, не с отдельными строками денежных операций. Будущий коннектор обязан забрать все страницы, устранить дубли по ID исходных операций и агрегировать их до передачи. Неуспешная/частичная выгрузка не должна считаться полным отчётом.

Закрытая неделя — основной источник для сверки, но не гарантия отсутствия будущих корректировок от площадки. Периодичность и статус окончательного финансового документа проверяются отдельно для WB и Ozon; произвольный документ Ozon нельзя назвать недельным только ради единой модели.

## Пример нормализованной версии

```js
{
  id: 'ID-отчёта-из-источника',
  marketplace: 'wb',
  accountId: 'ID-кабинета',
  source: 'weekly',
  revision: 1,
  from: '2026-10-12',
  to: '2026-10-18',
  closed: true,
  publishedAt: '2026-10-19T09:00:00Z',
  cells: [{date:'2026-10-12',article:'Артикул',metric:'revenue',value:92}]
}
```

Названия метрик в примере технические; они не заменяют карту реальных колонок пользовательского Excel. Схема внешнего API не угадывается по этому примеру.

## Дальнейшее подключение после получения XLSX

- Считать точные листы/колонки/формулы, сохранить контрольные примеры из таблицы.
- Сопоставить доступные показатели с актуальными API и различить дату заказа, продажи, финансовой операции и отчётного периода.
- Спросить себестоимость, планы и другие ручные поля только там, где они присутствуют в шаблоне и действительно недоступны из источников; не подставлять оценки без отметки.
- Настроить полные ежедневные выгрузки, повторную загрузку изменяемого недавнего периода и загрузку опубликованных закрытых недельных отчётов.
- Сохранять журнал атомарно на сервере с резервной копией и последним успешным состоянием. Сейчас модуль чистый: возвращает новое состояние журнала, файловая БД/планировщик ещё не добавлены.
- Подключить сверку к РНП, показать статусы предварительных/подтверждённых значений и расхождения. Вручную введённые поля хранить отдельно от API, чтобы сверка не стирала их.

## Проверка

`npm run test:rnp` проверяет ежедневные изменения, недельный приоритет в любом порядке импорта, повторные импорты без задвоения, защиту от поздних ежедневных правок, версии и корректировки, разделение кабинетов/маркетплейсов, сохранение истории и отсутствие выдуманных дневных значений.
